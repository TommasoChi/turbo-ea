# BO Relationship (ER-lite diagram for Business Objects)

**Spec status:** draft. Agreed Save, ownership, ER direction, editor permissions, Draw.io-style sync, shared positions and BO subtypes are recorded below.

## Goal

A new page under the **Application & Data** menu group, "BO Relationship": an automatic, macroscopic ER-style diagram of `DataObject` cards, showing which systems are master/slave of each data object and the relationships between data objects themselves.

## Approved mockup

[Open the interactive BO Relationship mockup](2026-10-28-data-relationship-design-assets/bo-relationship.html). Open the HTML in a browser to try the sample flows.

The mockup shows the folded Document corner, the legend below the diagram, and the card that opens in the right panel on left-click. The Indicators group shows the GDPR and payment badges.

## Scope

In scope:
- New page, menu entry under **Application & Data** → **BO Relationship**.
- **New ER relation type, DataObject ↔ DataObject.** It is separate from the lineage relation `relDataObjectSuccessor`. A-to-B and B-to-A are views of the same ER link. Store one relation per unordered BO pair and keep its original direction for the cardinality value (`1:1` / `1:n` / `n:1` / `n:m`).
- **At most one Master per Business Object.** Choose one linked Application as the authoritative source for the whole `DataObject`. Anagrafica clienti, Consensi privacy and Dati di spedizione equipment are separate BOs and can each have a different Master.
  - **Changing Master requires full access to the BO's Application links.** Only an editor with complete visibility and management authority over those links can assign, transfer or clear Master. Evaluate the capability from the caller's grants before inspecting the current designation. Editors with partial access get the same unavailable action whether a Master is visible, hidden or unset. The gate applies both to the card panel and to the Master choice when creating an Application link from the diagram.
  - Record the Master designation on the existing `relAppToDataObj` link. The other linked Applications display as **Slave** when a Master is assigned. CRUD flags remain independent of ownership.
  - With no Master, show all linked Applications under **Unclassified** (Da classificare). An authorized editor can replace the old Master designation in one operation. The former Master becomes Slave. Clearing the designation or removing the Master link returns the remaining Applications to Unclassified.
- **Diagram shapes and badges for `DataObject`.** Put the legend below the diagram. Source: `analisi-documenti/Projetti/Turbo-ea-prod/Business Application Management_V.0.2.xlsx`, sheet `Dati`.
  - **Required BO subtype.** Add the native `DataObject` subtypes **Data** (`data`) and **Document** (`document`) to the metamodel. Reuse existing keys that differ only in case, such as `Data` and `Document`, and keep existing card assignments. Both are BOs. Require a subtype when creating a BO. Use the approved mockup shapes. Data uses a rounded rectangle and Document uses a folded top corner. Existing BOs without a subtype stay readable and can be classified explicitly.
  - **GDPR**: badge icon shown when `isPersonalData` = true (field already exists).
  - **Payment data** (PCI-DSS scope): badge icon shown when a new `isPaymentData` boolean = true.
  - Group the two badges under **Indicators** in the right card panel. These are derived from the two booleans. Data Sensitivity (`dataSensitivity`) remains a separate card field.
  - `Categoria GDPR`, `Interessati`, `Retention`, `Tipo dato di pagamento` — **deferred**, not part of this pass; not needed for the diagram or its icons/shapes.
  - `Application Master` (the xlsx sheet's own text column) — represented by the Master designation on the Application link; maps to a *relation*, not a card field. **No bulk/automatic import** of the xlsx's existing data — populated by hand per object, same as any other card.
- **Diagram interaction:**
  - **Left-click a BO node to open that card immediately in the right-hand `CardDetailSidePanel`.** Use the selected `DataObject` ID and keep the diagram and Application panel usable alongside the non-modal card panel. Keyboard activation opens the same card.
  - **Canvas navigation follows ArchiMate.** Drag the background with the left mouse button to pan. The wheel pans vertically, Shift plus wheel pans horizontally, and Ctrl plus wheel zooms toward the pointer. Ctrl+plus and Ctrl+minus zoom, and Ctrl+0 fits the canvas. The keyboard shortcuts dialog lists commands available to the current user. The toolbar can hide or show the card panel. Selecting a BO opens its panel again.
  - **Canvas editing shortcuts.** Ctrl+A selects the visible BOs. Undo and Redo cover the current local draft. Copy and Paste open a new draft with an editable name for each copied BO, carrying its subtype and indicators. Delete removes selected BOs from the shared drawing on Save. Their cards and links stay in inventory. Sync shows the BO again at its saved position with its visible lines and Application links. Deleting a line still follows the confirmation and Sync flow. Space opens the card. Enter opens an unselected BO or renames the selected BO when editing is allowed. F2 also opens Rename. A draft name is local, and a saved card name follows the inventory edit and Sync flow.
  - A new panel on the **left** lists the linked Applications under **Master**, **Slave**, or **Unclassified**. Show name, link and role. Apply card visibility to the applications, the derived grouping and the role choices. A hidden Master must look like an unset Master to the viewer.
  - **Creating links from the diagram.** An editor can draw BO-to-BO ER links or connect an existing Application to a BO with the Application card picker. For the Application link, show the Master and Slave roles. Choosing Master assigns or transfers the sole Master. Slave is available when another Application is Master, including a Master staged earlier in the same save. When there is no visible Master, the editor can save the Application link as Unclassified. If a staged Master fails to save, keep its dependent Slave links pending and report that they are waiting for the Master.
  - The card panel can also edit existing links, including changing cardinality and assigning, transferring or clearing the Master. Access to write actions inside the BO page requires its edit permission. The card panel saves its own edits using the existing card workflow and triggers a new diagram check.
  - **Explicit Save.** Save persists new cards first, then eligible ER and Application links and their requested roles, then the accepted diagram changes and positions. Each successful operation stays saved if a later operation fails, following Draw.io's inventory sync behavior.
  - **Removing a line follows Draw.io.** Discard an unsaved line locally. When the user removes an existing ER line, ask whether to delete its real inventory relation. **No** restores the line. **Yes** queues the deletion. Delete from inventory only when the editor synchronizes the queued removal, individually or with **Sync all**. Save merges the editor's explicit visual changes into the latest shared drawing. If Save comes before removal sync, the line disappears from the shared drawing and the relation stays in inventory. Cancelling a queued removal restores the line in the open drawing. A failed deletion stays pending and can be retried or cancelled, including after Sync all.
  - **Close and reopen follow Draw.io's draft recovery.** The editor keeps a browser-local drawing draft, refreshed about every five seconds, separate from the shared diagram. Reopen the last shared version and offer Restore or Discard when a local draft differs. Restoring brings back the unsaved drawing and recoverable staged additions on that browser. Discard removes the local draft. A successful Save clears the saved edits from it and retains anything still pending. Save and Exit follows the normal Save flow. Warn before browser unload when inventory sync operations are pending.
  - **The removal queue is session-only.** The restored drawing may still lack the line, but reopening or restoring starts with an empty outgoing deletion queue. Only a new deliberate, confirmed removal can queue an inventory delete. Recheck the restored drawing against inventory. A readable relation that still exists can be offered as an incoming change so the editor can restore the line. A completed inventory deletion stays completed across sessions.
  - **Concurrent removals of different lines are merged.** If two editors start from the same saved diagram and remove different lines, both removals survive their Saves. Merge visual changes by relation ID and preserve edits to untouched lines, including lines outside the editor's scope. This rule applies to the shared drawing. Inventory deletions still require confirmed removal and Sync.
  - **Only a deliberate line removal queues deletion.** Filtering, removing a node from the drawing or applying an inventory change notice never deletes relations in inventory.
  - **Partial success is visible and retryable.** If `Ordine` is created but its link to `Cliente` fails, the card stays in the inventory and the editor identifies the link as pending. Retrying submits only pending work and recovers the identity of an already created card if its response was lost. The retry creates no duplicate card or relation.
- **Diagram library:** reuse `diagram-js` (+ `diagram-js-direct-editing`), already a project dependency and already used by `DiagramEditor`/`DiagramViewer` for ArchiMate/BPMN diagrams. No new dependency.
- **Layout and overlap avoidance:** reuse `@dagrejs/dagre`, already a project dependency (`frontend/src/features/reports/layeredDependencyLayout.ts` already uses it for the Layered Dependency View) to compute node positions and edge routing with minimal overlap.
- **Shared positions.** Keep saved positions fixed. Compute local proposals for nodes without a saved position and share manual moves or accepted proposals only on explicit Save. When two editors move the same node, use the pair of coordinates from the last Save that successfully writes that node's position. This follows Draw.io's last-save rule and also applies when other operations in that BO Save remain pending. Merge only the edited coordinates so simultaneous moves of different nodes both survive. Automatic proposals only fill missing positions.
- **Workspace transfer.** Include the last saved BO drawing and coordinates in the workspace bundle, following Draw.io. Import them when the target has no saved BO drawing, including when it has an initialized but unsaved placeholder. Preserve an already saved target drawing and its positions on re-import. Remap card and relation IDs to their target values while keeping coordinates. Browser drafts, pending removals and operation receipts stay local to their original session or workspace.
- **Cardinality is optional and descriptive.** The value labels the relationship and does not impose a constraint on how many BOs can be linked. Use a dedicated helper for the reserved `cardinality` attribute. Swap `1:n` and `n:1` when reading or editing from the opposite end. `1:1` and `n:m` are symmetric. Saving from the opposite end converts the value back to the original stored direction.

- **Inventory check and sync, following Draw.io.** On each load, open the last saved diagram and compare it with readable inventory data. Flag relevant changes without applying them automatically. Recheck on demand. An editor can choose **Sync** to apply inventory changes to the open diagram, keeping manual positions. The next **Save** shares the refreshed diagram and any position changes. Include renamed, changed-subtype, archived or deleted BOs and changed or removed links. Detect additions too because the BO view covers the readable inventory. Filter the saved snapshot and the change list by card visibility. Sync and Save preserve entries the editor cannot read. Compare a fresh view on the first load if no saved diagram exists.
- **Diagram scope and filtering.** Include readable `DataObject` cards, including isolated nodes. Reuse `FilterSidebarSection` for personal data (`isPersonalData`) and payment data (`isPaymentData`) in the first pass. `Categoria GDPR` remains deferred. Additional metamodel filters and inventory-grid badges are deferred.
- **Ownership granularity is the Business Object.** Each card represents one BO and has its own optional Master. Attributes within the same BO, such as first name and surname within Anagrafica clienti, share that designation.
- **Access control.** Administrators can view and edit BO Relationship. Other users are view-only by default. The `boRelationship.view` and `boRelationship.edit` permissions allow later role and group configuration. Save, Sync and write actions in the page and its card panel require edit permission plus the applicable underlying card or relation permissions.

Out of scope (not asked, not assumed):
- Any card type other than `DataObject` and `Application` as diagram participants (e.g. no `BusinessCapability` node layer here — that concept belongs to the cost-report Sankey's group_by, a different feature on the same branch).
- Autosave of new objects/relations (explicit Save only, per above).
- Inferring master/slave from CRUD flags (explicit, independent field).
- Bulk/automatic import of the xlsx's existing `Dati` sheet data (per above — populated by hand).
- `Categoria GDPR`, `Interessati`, `Retention`, `Tipo dato di pagamento` as new fields (deferred, per above).

## Current state (verified, not assumed)

- The `DataObject` card type exists in Application & Data. Its current seed has no Data/Document subtypes and no payment-data field.
- `relAppToDataObj` relation type exists (`source_type_key: "Application"`, `target_type_key: "DataObject"`, `cardinality: "n:m"` at the type level, `attributes_schema`: `crudCreate`/`crudRead`/`crudUpdate`/`crudDelete` booleans). No master/slave attribute today.
- `relDataObjectSuccessor` is an existing `DataObject` ↔ `DataObject` lineage relation. The new ER relation is a separate metamodel type.
- `Relation.attributes` is a free-form JSONB column (`backend/app/models/relation.py`), already the mechanism CRUD uses — store the explicit Master marker and cardinality in that column. Enforce one ER link per unordered pair and at most one Master across write paths and concurrent saves.
- `RelationType.cardinality` (`backend/app/models/relation_type.py`) is a fixed type-level column (`"1:1"`/`"1:n"`/`"n:m"`), separate from the per-instance cardinality value this spec adds — the type-level column stays at its default and is not what drives the diagram's displayed value.
- `diagram-js`/`diagram-js-direct-editing` and `@dagrejs/dagre` are both already project dependencies (`frontend/package.json`), used respectively by the diagram editors and the Layered Dependency View.
- Reuse the existing `CardDetailSidePanel` with a BO-specific edit gate and a refresh hook after supported changes.

## Agent's calls

- Derive visible Application groups from links the viewer can read. A hidden Master has the same visible result as an unset Master.
- Keep failed deletions in the queue after Sync all, consistent with the partial-success retry policy. Draw.io keeps failed single removals pending.
- Display a neutral shape for an existing BO without a subtype and allow explicit classification. The migration does not infer Data or Document from the name.
- Keep Applications in the selected BO's side panel. The diagram's link action can pick them and assign the role. Edits saved from the card panel use its existing workflow and show up in the canvas change check.
