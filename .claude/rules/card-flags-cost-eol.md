# Card health flags, EOL coverage and fiscal-year cost rules

> Loaded when you touch `backend/app/services/card_flags.py`, `backend/app/services/lifecycle.py`, `backend/app/services/fiscal_year.py`, `backend/app/services/eol_service.py`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

- **A cross-cutting card health flag has exactly one definition, in `backend/app/services/card_flags.py`.** "Orphaned" and "stale" are each read by three surfaces — an inventory filter (`GET /cards?<flag>=true`), a Data Quality KPI tile with its drill-down panel (`GET /reports/data-quality` + `?scope=`), and a deep link from one to the other (`buildInventoryFlagUrl`) — so if the definitions diverged, clicking a count of 37 would land on a grid showing something else. The same module owns **EOL coverage** (added 2.122.0 for [#1065](https://github.com/vincentmakes/turbo-ea/discussions/1065)): `has_eol_coverage` is an endoflife.date link (`attributes.eol_product` *and* `eol_cycle`) **or** a manual `lifecycle.endOfLife` date — the manual date is the company's own decommission date, which the EOL report has always accepted in its own right, so "not recorded" has to mean neither. Its consumers are the EOL report's `missing` rows and the Data Quality report's coverage chart — which exists in **both forms**, counted in Python for the dashboard totals and queried in SQL by `eol_bucket_condition` for the chart's drill-down panel, so `tests/services/test_eol_coverage.py` runs the two over a matrix of awkward JSONB shapes and pins them equal. Write those SQL negations **positively** (`_jsonb_absent`): `attributes->>'eol_product'` is SQL NULL for an absent key *and* for JSON null, and `NOT NULL` is not TRUE, so `not_(and_(...))` silently drops exactly the cards a "nothing recorded" filter exists to find. `EOL_TYPES` (Application, ITComponent) is the eligible population — EOL is not a metamodel concept, so it cannot be derived from `fields_schema` — mirrored on the frontend by `frontend/src/lib/eol.ts`, which also owns the per-status colours the EOL report and the inventory column share. Resolving a *status* (as opposed to coverage) is an outbound call to endoflife.date, so it lives in `backend/app/services/eol_service.py` behind a 30-minute per-product cache, and `GET /eol/card-status` commits its session before calling it. Guard tests: `backend/tests/services/test_eol_coverage.py`, `tests/api/test_reports_eol.py`, `tests/api/test_reports_extended.py`.

- **The cost reports take an optional `fiscal_year`, and "does this card's cost count" in the current year has one definition: `is_live_in_fiscal_year` (`backend/app/services/lifecycle.py`).** An annual cost counts **in full** when the current fiscal year falls between the one the card goes `active` in and the one its `endOfLife` falls in, both ends included — deliberately no pro-rating. Missing dates follow the time-travel reports' `hasStartedByDate` (`features/reports/portfolioHelpers.ts`): a `plan`/`phaseIn` date without `active` is still planned, no start date means always started, no `endOfLife` means never retires — so a card with no lifecycle always counts. `GET /reports/cost-treemap` and `GET /reports/cost` serve the current year (no `fiscal_year`, or equal to it) from live attributes gated by `is_live_in_fiscal_year`, the related cards an aggregate sums included; any other year lists cards by their recorded cost, with no lifecycle gate (`backend/app/services/cost_report.py::cards_with_cost`: readable, non-archived cards with a non-zero `card_cost_history` row for that year). Both responses carry `fiscal_year` (the requested year), `current_fiscal_year` and `fiscal_year_start`, so the page can name the years (`CostReport`'s picker and toolbar chip); `PUT /cards/{id}/cost-history` accepts `current-5` … `current+1` (the forecast year, typed by hand). Fiscal-year arithmetic (`fiscal_year_for`, `current_fiscal_year`, `get_fiscal_year_start`, a year named after the calendar year it **ends** in) lives in the leaf `backend/app/services/fiscal_year.py` (re-exported by `calculation_ppm.py`); the frontend's `fiscalYearLabel` (`frontend/src/lib/fiscalYear.ts`) names a fiscal year in PPM, while the cost report uses its own `FYnn - Current/Forecast` names. Guard tests: `tests/services/test_lifecycle.py`, `tests/services/test_cost_report.py`, `tests/api/test_reports_cost_fiscal_year.py`, `CostReport.test.tsx`.

- **The cost treemap and the cost Sankey take the same parameters and the same validation, and a cost is counted exactly once in both.** `GET /reports/cost-treemap` and `GET /reports/cost-sankey` take `type` (one card-type key or several, comma-separated — Application, ITComponent, Initiative, or a combined list; each must own cost fields), `cost_field`, `fiscal_year` and `group_by`. `group_by` is `field:<key>` (a single-valued field; multiple-choice fields are refused) or `rel:<key>` (a relation type), parsed by `parse_group_by` in `backend/app/services/cost_grouping.py`; a bare legacy key reads as `field:<key>`, an unknown one loads ungrouped. A relation is a valid group only where each card has at most one link of that type, read as `relations.py::_require_cardinality_room` reads it: `1:n` constrains the **source** end (the source card has at most one target, so only the source side is grouped), `1:1` either end, `n:m` never. A card with no value or link falls in the `__other__` sentinel (`OTHER_GROUP`); the server returns raw values (option value, `true`/`false`, linked card name) and the page translates option labels, Yes/No and "Other". The treemap response carries `components`: the cost fields concurring to `cost_field` (`backend/app/services/cost_components.py::cost_components` — the `data.<key>` references of the active calculation that targets the total field, else the total field itself), which the history chart stacks, labelled by technical key and shown only while the Forecast year is selected. The Sankey has three columns — cost items, then groups (only when `group_by` is set), then cards — built by `cost_report.py::build_cost_sankey`; it never draws card-to-card flows, because an IT Component shared by several applications would be counted once per application. Guard tests: `tests/services/test_cost_components.py`, `tests/services/test_cost_grouping.py`, `tests/api/test_reports_cost_types.py`, `tests/api/test_reports_cost_sankey_parity.py`, `CostReport.test.tsx`, `CostTrendChart.test.tsx`, `costTreemapOption.test.ts`, `costSankeyOption.test.ts`, `costTrendOption.test.ts`.
