# Card health flags, EOL coverage and fiscal-year cost rules

> Loaded when you touch `backend/app/services/card_flags.py`, `backend/app/services/lifecycle.py`, `backend/app/services/fiscal_year.py`, `backend/app/services/eol_service.py`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

- **A cross-cutting card health flag has exactly one definition, in `backend/app/services/card_flags.py`.** "Orphaned" and "stale" are each read by three surfaces — an inventory filter (`GET /cards?<flag>=true`), a Data Quality KPI tile with its drill-down panel (`GET /reports/data-quality` + `?scope=`), and a deep link from one to the other (`buildInventoryFlagUrl`) — so if the definitions diverged, clicking a count of 37 would land on a grid showing something else. The same module owns **EOL coverage** (added 2.122.0 for [#1065](https://github.com/vincentmakes/turbo-ea/discussions/1065)): `has_eol_coverage` is an endoflife.date link (`attributes.eol_product` *and* `eol_cycle`) **or** a manual `lifecycle.endOfLife` date — the manual date is the company's own decommission date, which the EOL report has always accepted in its own right, so "not recorded" has to mean neither. Its consumers are the EOL report's `missing` rows and the Data Quality report's coverage chart — which exists in **both forms**, counted in Python for the dashboard totals and queried in SQL by `eol_bucket_condition` for the chart's drill-down panel, so `tests/services/test_eol_coverage.py` runs the two over a matrix of awkward JSONB shapes and pins them equal. Write those SQL negations **positively** (`_jsonb_absent`): `attributes->>'eol_product'` is SQL NULL for an absent key *and* for JSON null, and `NOT NULL` is not TRUE, so `not_(and_(...))` silently drops exactly the cards a "nothing recorded" filter exists to find. **Which types track End of Life is the type's own `eol` section toggle** (Card Layout editor, `section_config.eol.hidden`), decided by `type_tracks_eol` in `card_flags.py` and mirrored by `typeTracksEol` in `frontend/src/lib/eol.ts`: an explicit boolean wins; absent (or a legacy bare boolean / a config with no `hidden`), the shipped default `DEFAULT_EOL_TYPES` (Application, ITComponent) applies — so no migration was needed and every new custom type starts hidden. Before 2.188.0 the list was hard-coded and the card section rendered nothing elsewhere while the layout switch read "visible". The one toggle drives every EOL surface: the card section and create-dialog link, `/reports/eol`, the data-quality coverage chart and drill-down, the dashboards' `eol_*` flags and `eol_coverage` dimension (`ResolvedQuery.eol_types`), the inventory column/filter (`eolColumnApplies(types, keys)`), bulk linking, `/eol/card-status`, `GET /eol/types` and the extension SDK's `get_eol_status`. Callers load `eol_type_keys(db)` once per request and pass it as `eol_types=` to `eol_bucket_condition` / `eol_coverage_key` — never re-add a fixed list. The Card Layout editor shows the **effective** state on the eol row and writes an explicit `hidden` when toggled. Hiding EOL on a type never touches its cards' `eol_*` attributes or lifecycle dates; the EOL report's IT Component → Application impact still names applications when Application itself stops tracking EOL. `frontend/src/lib/eol.ts` also owns the per-status colours the EOL report and the inventory column share. Resolving a *status* (as opposed to coverage) is an outbound call to endoflife.date, so it lives in `backend/app/services/eol_service.py` behind a 30-minute per-product cache, and `GET /eol/card-status` commits its session before calling it. Guard tests: `backend/tests/services/test_eol_coverage.py` (incl. `TestWhichTypesTrackEol`), `tests/api/test_reports_eol.py`, `tests/api/test_reports_extended.py`, `tests/api/test_eol.py::TestEolTypesFollowTheSectionToggle`, `frontend/src/lib/eol.test.ts`, `CardLayoutEditor.test.tsx` ("End of Life follows the type's real state").

- **The cost reports take an optional `fiscal_year`, and "does this card's cost count" in the current year has one definition: `is_live_in_fiscal_year` (`backend/app/services/lifecycle.py`).** An annual cost counts **in full** when the current fiscal year falls between the one the card goes `active` in and the one its `endOfLife` falls in, both ends included — deliberately no pro-rating. Missing dates follow the time-travel reports' `hasStartedByDate` (`features/reports/portfolioHelpers.ts`): a `plan`/`phaseIn` date without `active` is still planned, no start date means always started, no `endOfLife` means never retires — so a card with no lifecycle always counts. `GET /reports/cost-treemap` and `GET /reports/cost` serve the current year (no `fiscal_year`, or equal to it) from live attributes gated by `is_live_in_fiscal_year`, the related cards an aggregate sums included; any other year lists cards by their recorded cost, with no lifecycle gate (`backend/app/services/cost_report.py::cards_with_cost`: readable, non-archived cards with a non-zero `card_cost_history` row for that year). **Application and IT Component are the exception: their amount is the TCO from `card_costs` (see `cost-items.md`), still gated by `is_live_in_fiscal_year` in the current year.** Both responses carry `fiscal_year` (the requested year), `current_fiscal_year` and `fiscal_year_start`, so the page can name the years (`CostReport`'s picker and toolbar chip); `PUT /cards/{id}/cost-history` accepts `current-5` … `current+1` (the forecast year, typed by hand) for the types that still use cost fields (Application and IT Component answer 409: they use `/cards/{id}/costs`). Fiscal-year arithmetic (`fiscal_year_for`, `current_fiscal_year`, `get_fiscal_year_start`, a year named after the calendar year it **ends** in) lives in the leaf `backend/app/services/fiscal_year.py` (re-exported by `calculation_ppm.py`); the frontend's `fiscalYearLabel` (`frontend/src/lib/fiscalYear.ts`) names a fiscal year in PPM, while the cost report uses its own `FYnn - Current/Forecast` names. Guard tests: `tests/services/test_lifecycle.py`, `tests/services/test_cost_report.py`, `tests/api/test_reports_cost_fiscal_year.py`, `CostReport.test.tsx`.

- **The cost treemap and the cost Sankey take the same parameters and the same validation, and a cost is counted exactly once in both.** `GET /reports/cost-treemap` and `GET /reports/cost-sankey` take `type` (one card-type key or several, comma-separated — Application, ITComponent, Initiative, or a combined list; each must own cost fields), `cost_field`, `fiscal_year` and `group_by`. `group_by` is `field:<key>` (a single-valued field; multiple-choice fields are refused) or `rel:<key>` (a relation type), parsed by `parse_group_by` in `backend/app/services/cost_grouping.py`; a bare legacy key reads as `field:<key>`, an unknown one loads ungrouped. A relation is a valid group only where each card has at most one link of that type, read as `relations.py::_require_cardinality_room` reads it: `1:n` constrains the **source** end (the source card has at most one target, so only the source side is grouped), `1:1` either end, `n:m` never. A card with no value or link falls in the `__other__` sentinel (`OTHER_GROUP`); the server returns raw values (option value, `true`/`false`, linked card name) and the page translates option labels, Yes/No and "Other". The treemap response carries `components`: the cost fields concurring to `cost_field` (`backend/app/services/cost_components.py::cost_components` — the `data.<key>` references of the active calculation that targets the total field, else the total field itself; for Application and IT Component, the catalogue item keys, archived included, labelled through the response's `item_labels`), which the history chart stacks, labelled by technical key and shown only while the Forecast year is selected. The Sankey has three columns — cost items, then groups (only when `group_by` is set), then cards — built by `cost_report.py::build_cost_sankey`; it never draws card-to-card flows, because an IT Component shared by several applications would be counted once per application. Guard tests: `tests/services/test_cost_components.py`, `tests/services/test_cost_grouping.py`, `tests/api/test_reports_cost_types.py`, `tests/api/test_reports_cost_sankey_parity.py`, `CostReport.test.tsx`, `CostTrendChart.test.tsx`, `costTreemapOption.test.ts`, `costSankeyOption.test.ts`, `costTrendOption.test.ts`.

- **The cost report page (`CostReport.tsx`) offers Application and IT Component only, and its three views (treemap, Sankey, table) share one state: the cost-type selector, one colour plan, one drill, one trend.** The selector lists **TCO** plus one option per catalogue item from `/metamodel/cost-item-types` (archived included, sorted by `sort_order`); **TCO is always the sum of every item, archived ones included** (same rule as `card_costs.year_costs`), so the table's TCO column never differs from the card's. Per-card, per-item amounts come only from `/reports/cost-sankey` (`nodes[].costs`, hook `useCostBreakdown`), never from N treemap calls; the treemap `items` carry one `cost` each. **Left click opens the side card, right click drills** (`EChart` `onContextMenu`; the native menu is blocked only over the chart/table), in all three views. The drill state is `costDrill.ts` (card, group, Others), climbs one level with the breadcrumb Back, lives in component state and resets when type, cost type, group-by or fiscal year change. **Colours come from `costColors.ts`, never a raw hex**: groups take the validated `CHART_CATEGORICAL` hues in size order (largest first, on the scoped totals of the selected cost, the same in every view), members are shades of the group hue (darker = costlier), groups beyond the 8th fold into one real grey **Others** (`OTHERS_KEY`, in all three views, drillable into its members), and the no-group bucket (`__other__`, "Unspecified") stays a separate lighter grey with its own legend entry, so there are never two identical "other"s; an ungrouped card takes a stable colour hashed from its name (`cardColor`). Tile text and delta badges follow tile luminance (`inkOn`, the `*_ON_LIGHT` tokens). Every tile, node and table row carries a type badge (icon + type name through `useTypeLabel`). The yearly trend (`CostTrendChart`) shows above all three views in the Forecast year and follows the drill and the scope: its series are the whole catalogue for TCO and `[costField]` for a single item (the backend's `components` rule), and its fetches are keyed only on type, cost field, components, years and `group_by`, so a drill or scope change re-derives rows without refetching. Guard tests: `CostReport.test.tsx`, `CostReport.branches.test.tsx`, `CostReport.mutation.test.tsx`, `costColors.test.ts`, `costDrill.test.ts`, `CostLegend.test.tsx`, `useCostBreakdown.test.ts`, `CostTrendChart.test.tsx`.
